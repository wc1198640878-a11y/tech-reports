# 自动闪避 Mod 运作原理（续篇）

> 上一份报告讲的是"三个方案各是什么、为什么都不行"。
> 这一份讲**底层机制**：一个 C# mod 到底是怎么活在你游戏里的、Harmony 打补丁在物理上做了什么、
> 以及——**为什么它会时灵时不灵**。这是这几天真正搞明白的东西。
>
> 写给零编程基础但愿意理解原理的人。看不懂的术语都配了大白话。

---

## 零、先用一个比喻串起全文

想象游戏是一个**公司**，里面有两个部门：

```
┌───────────────────────────────────────────────┐
│  原生层（C++ 编译出的机器码）                    │
│  工厂车间：渲染画面、物理碰撞、播放动画、读键鼠    │
│  只有机器码 —— 相当于一本已经翻译成外语的书，     │
│  你能翻，但找不到"第几章第几节"                  │
└───────────────────────────────────────────────┘
                    ↕  USharp 桥
┌───────────────────────────────────────────────┐
│  逻辑层（C# 编译出的 IL 中间语言）                │
│  管理办公室：伤害怎么算、闪避判定、敌人 AI        │
│  有类名、方法名 —— 相当于原版书，目录清清楚楚      │
└───────────────────────────────────────────────┘
```

**自动闪避是"管理办公室"的业务**（闪避判定是逻辑，不是画面），所以应该改 C# 层。

而改 C# 层最常用的工具叫 **Harmony**。这篇报告的主角就是它——**以及它为什么会失灵**。

## 一、一个 C# mod 是怎么"活"在游戏里的

游戏本来不认识任何 mod。要让自己的代码跑进游戏进程，需要三步：

### 第一步：混进门（DLL 劫持）

Windows 加载程序时有个规则：**先看 exe 所在目录，再看系统目录**。

所以把游戏本来就会加载的系统 DLL（比如 `version.dll`）换成一个"冒牌货"：

```
CSharpLoader 的 version.dll（303 KB，未签名）
    ├── 转发所有原版功能   ← 游戏察觉不到异常
    └── 顺便启动 .NET 运行时，加载 CSharpLoader
```

**这是所有 mod 加载器的通用套路**，UE4SS 用 `dwmapi.dll`，CSharpLoader 用 `version.dll`。

> ⚠️ 有个坑：如果那个 DLL 名字在 Windows 的 **KnownDLLs** 名单里，系统会强制从
> `C:\Windows\System32` 加载，冒牌货永远不生效。我查过你这台机器，
> 31 项名单里**没有** `version.dll` 和 `dwmapi.dll`，所以这条路是通的。

### 第二步：认亲（`ICSharpMod` 接口）

CSharpLoader 启动后会扫描 `CSharpLoader\Mods\` 下每个子目录里的 `.dll`，
找里面**实现了 `ICSharpMod` 接口**的类：

```csharp
public interface ICSharpMod
{
    string Name { get; }      // mod 名字
    string Version { get; }   // 版本
    void Init();              // 加载时调用
    void DeInit();            // 卸载时调用
}
```

**这就是 mod 的"入场券"。** 控制台里那行日志就是认亲成功的证据：

```
[D] ======== Loading CSharpLoader\Mods\PerfectDodgeV2.4\PerfectDodgeV2.4.dll ========
[D] Found ICSharpMod: PerfectDodgeV2.PerfectDodgeMod
```

### 第三步：干活（在 `Init()` 里打补丁）

```csharp
public void Init()
{
    LoadConfig();                                        // 读 config.json
    harmony = new Harmony("PerfectDodgeV2.4");
    harmony.PatchAll(Assembly.GetExecutingAssembly());   // ← 核心：打补丁
    Logger.Log("PerfectDodgeV2.4 initialized successfully.");
}
```

**`PatchAll` 会自动扫描自己程序集里所有带 `[HarmonyPatch]` 标记的类，逐个挂上去。**

**关键点**：这一步只要有一个目标方法找不到，就会抛异常。而它打印了
`initialized successfully` —— 说明**6 个补丁全部挂到了真实存在的方法上**。
这也排除了"版本不匹配"这个可能。

## 二、为什么 C# 层比 C++ 层好啃

这是理解一切的前提。

| | C++ 层（原生） | C# 层（托管） |
|---|---|---|
| 编译产物 | **机器码** | **IL（中间语言）** |
| 里面有什么 | 只有指令，没有名字 | **类名、方法名、参数名全在** |
| 怎么找目标 | 靠"特征码搜索"—— 猜一段字节序列 | 直接按名字找 |
| 游戏更新后 | 特征码大概率失效，**全废** | 方法名通常不变，**还能用** |

**打个比方**：

- **机器码** = 一本已经译成外语的书。你想改第 3 章，得先靠内容猜哪一页是第 3 章。
- **IL** = 原版书，目录、章节标题清清楚楚。**直接翻到 `BUS_BeAttackedComp` 这一节就行。**

而 **Harmony 就是一个"能在任意一页插入便签"的工具**——不需要原书作者同意，也不需要重新排版。

> 这也解释了为什么 C++ 那套（UE4SS）在黑猴上彻底失败：
> 游科大幅改造了引擎（几百个 `GS*` 自研插件），而 **UE4SS 的特征码表里根本没有黑猴**
> （它的"按游戏定制配置"只有 14 个别的游戏）。**猜不到章节，自然改不了书。**

## 三、Harmony 到底做了什么（核心原理）

### 3.1 物理过程：在方法门口装一个"传送门"

C# 的方法被编译成机器码后，在内存里是一段连续的代码，有**唯一的入口地址**。

Harmony 干的事非常直接：

```
打补丁前：
    0x1000:  push rbp          ← 方法入口
    0x1001:  mov rbp, rsp
    0x1004:  ... 原方法逻辑 ...

打补丁后：
    0x1000:  jmp 0x9000        ← 入口被改成了跳转！
    0x1005:  ... 原方法逻辑 ...

    0x9000:  ... 你的补丁代码 ...
             跳回原方法（或者不跳）
```

**任何人想调用这个方法，都会先被"传送"到你的代码。** 这就是 detour（绕行）。

### 3.2 三种插入方式

Harmony 让你在三个位置插入代码：

| 类型 | 位置 | 能做什么 |
|---|---|---|
| **Prefix** | 原方法**执行前** | **可以返回 `false` 取消原方法！** |
| **Postfix** | 原方法**执行后** | 能看到结果，可以改结果 |
| **Transpiler** | 修改原方法内部的 IL | 最强大也最难 |

**`Prefix` 能"取消原方法"这一条是关键**——它就是"精准闪避"能实现的根本原因。

### 3.3 一个真实的例子（原 mod 的核心）

```csharp
[HarmonyPatch(typeof(BUS_BeAttackedComp), "OnHandleNormalDamageEffect")]
public static class Patch_OnHandleNormalDamageEffect
{
    public static bool Prefix(BUS_BeAttackedComp __instance,        // ← 自动注入：被补丁的对象
                              AActor Attacker,
                              ref FSkillDamageConfig SkillDamageConfig)
    {
        // ① 判断被打的是不是玩家
        var owner = __instance.GetOwner() as APawn;
        if (owner == null || !owner.IsPlayerControlled()) return true;

        // ② 玩家正在精准闪避 → 返回 false，整个伤害结算被取消
        if (Helper.IsPlayerPreciseDodgeActive()) return false;

        // ③ 要挨打了 → 触发一次闪避
        if (AutoDodgeOnAttack && !Helper.IsPlayerDodgeActive())
        {
            int dir = GetRandomDodgeDirection();
            FindPreciseDodgeComp(__instance).TryPreciseDodge(dir);
        }
        return true;   // 放行
    }
}
```

**几个自动注入的魔法参数**（Harmony 的约定，名字固定）：

| 参数 | 拿到什么 |
|---|---|
| `__instance` | 被补丁的那个对象（相当于 `this`） |
| `__result` | 原方法的返回值（配 `ref` 就能改） |
| `__originalMethod` | 当前正在补丁的方法是哪个 |

**这段代码浓缩了整个 mod 的思路**：

```
拦截 —— 在"伤害结算"这条必经之路上设卡
判定 —— 我该不该闪？
执行 —— 调用游戏自己的闪避技能（不自己造）
放行 —— 该怎样还怎样
```

**特别注意它避开的两个坑**：
- **不自己控制角色移动** —— 而是调游戏现成的 `TryPreciseDodge`
- **不模拟按键** —— 而是调游戏现成的输入接口 `InputActionTrigger`

**能少碰游戏内部，就少一分崩溃风险。这是很成熟的做法。**

## 四、为什么 Harmony 有时会失灵 —— JIT 内联

**这是整晚最大的收获，也是它时灵时灵的根本原因。**

### 4.1 用大白话解释"内联"

C# 代码先编译成 IL，**运行时再把 IL 编译成机器码**（这个过程叫 JIT = Just-In-Time）。

在 JIT 编译时，编译器会做很多优化，其中一个叫**内联**：

```csharp
// 原代码
int GetWindow() { return 180; }        // 一个很短的方法

void CheckDodge() {
    int w = GetWindow();               // 调用它
    if (elapsed < w) { PerfectDodge(); }
}
```

**JIT 一看：`GetWindow` 就一行，调用它还要压栈、跳转、返回，太亏了。于是它直接把 `180` 抄进 `CheckDodge` 里：**

```csharp
void CheckDodge() {
    int w = 180;                       // ← 方法调用消失了，被"抄"进来了
    if (elapsed < w) { PerfectDodge(); }
}
```

**这就是内联。** 好处是快，代价是——**`GetWindow` 这个方法从此没人调用了。**

### 4.2 为什么这会杀掉补丁

**回到那个比喻**：

> 在方法门口装了一个传送门（Harmony patch）。
> 但如果调用方在编译时，**已经把被调用方的代码抄进了自己家里**——
> 那它根本不会走到那个门口，**传送门就白装了。**

```
         ┌─────────────────────────────┐
         │  CheckDodge（调用方）        │
         │                             │
         │   ┌─────────────────────┐   │
         │   │ 抄来的 GetWindow 副本 │   │  ← 这份副本不经过任何"门"
         │   └─────────────────────┘   │
         └─────────────────────────────┘
                      ✗ 传送门在这里，但没人经过
         ┌─────────────────────────────┐
         │  GetWindow 的入口 → 传送门   │
         └─────────────────────────────┘
```

**而这个 mod 的 6 个目标，全是"短方法"——正是最容易被内联的那一类：**

| 目标方法 | 为什么容易被内联 |
|---|---|
| `get_PreciseDodgeTolerantTimeSeconds` | 属性读取器，本质就一行 `return xxx` |
| `InPreciseDodgeWindow` | 判定函数，几行 |
| `OnTickWithGroup` | 派发函数，几行 |
| `InputActionTrigger` | 转发函数 |
| `Invoke` | 事件调用 |
| `OnHandleNormalDamageEffect` | 唯一稍大的，但仍可能被内联 |

### 4.3 我自己踩的坑（这个教训最值钱）

我写诊断工具时，放了一个"自检"——**先证明 Harmony 在这个进程里能用，再去测游戏**。逻辑上很严谨：

```csharp
public static void SelfTarget() { SelfTargetCalls++; }     // 目标方法
public static void SelfPostfix() { SelfPostfixCalls++; }   // 补丁

// 挂上补丁，然后调用 3 次
harmony.Patch(SelfTarget, postfix: SelfPostfix);
SelfTarget(); SelfTarget(); SelfTarget();

// 结果：目标被调用 3 次，补丁被调用 0 次 → 判定"Harmony 失效"
```

**这个自检从头到尾一直在报"失败"。**

而我基于它得出的第一个结论是**错的**——因为**在唯一成功的那次会话里，这个自检照样报失败**：

```
23:53:40.501  【对照组】Harmony 自检：目标被调用 3 次，补丁被调用 0 次 -> ✗✗
（而同一份日志后面：探针触发 16,602,969 次）
```

**原因就是内联**：`SelfTarget()` 太短，被 JIT 抄进了调用方，那 3 次调用压根没经过"门"。

**修法**：给目标方法加一个标记，明确禁止内联：

```csharp
[MethodImpl(MethodImplOptions.NoInlining)]
public static void SelfTarget() { ... }
```

**这个坑的价值在于**：它证明了内联不是理论，**它就在我眼皮底下发生了**。所以"游戏补丁被内联绕过"这个推测，有一个非常硬的旁证。

> **教训**：设计实验时，对照组本身也可能被同样的机制污染。
> **一个实验如果"永远失败"，那它测的可能不是被测对象，而是它自己的缺陷。**

## 五、那个 mod 的真实设计（反编译还原）

### 5.1 六个补丁的分工

| 补丁挂在哪 | 类型 | 干什么 |
|---|---|---|
| `BUS_BeAttackedComp:OnHandleNormalDamageEffect` | Prefix | **检测 + 拦截**：挨打时触发闪避 / 取消伤害 |
| `FInputActionProcessor:InputActionTrigger` | Prefix | **执行**：记住输入处理器实例，供后面调用 |
| `BUC_PreciseDodgeData:get_PreciseDodgeTolerantTimeSeconds` | Postfix | 把判定窗口从 180ms 改成 1000ms |
| `BUC_PreciseDodgeData:InPreciseDodgeWindow` | Postfix | 强制判定"你正处于完美闪避窗口" |
| `GSDel_CastSkillWithAnimMontage:Invoke` | Prefix | 技能 / 动画相关 |
| `BPS_PlayerInteractComp:OnTickWithGroup` | Postfix | 每帧一次：读 `I` 热键、置 `IsInGame` |

### 5.2 完整数据流

```
① 检测   敌人攻击 → 伤害进入结算流程
             ↓
② 拦截   OnHandleNormalDamageEffect 的前缀被触发
             ↓
③ 判定   IsInGame？AutoDodgeOnAttack？玩家在闪避吗？
             ↓
④ 决策   随机选方向（左/右/后，不往前）
             ↓
⑤ 执行   调 BUS_PreciseDodgeComp.TryPreciseDodge(方向)
             ↓
⑥ 收尾   如果玩家已在闪避 → return false，这次伤害被吞掉
```

### 5.3 致命缺陷：单点故障

反编译后我把 `IsInGame` 的每一次出现都列了出来：

```
第  48 行：  public static bool IsInGame = false;        ← 默认关
第 934 行：  PerfectDodgeMod.IsInGame = true;            ← 全文唯一置位处！
第 625/648/671/700/796 行： if (!IsInGame) return;       ← 5 个补丁全部依赖它
```

**"全文唯一置位处"落在 `BPS_PlayerInteractComp:OnTickWithGroup` 这一个 tick 补丁里。**

**而这个 tick 恰恰是"时灵时不灵"的那一类。**

```
tick 补丁跑通  →  IsInGame 变 true  →  整个 mod 活过来
tick 补丁被绕过 →  IsInGame 永远 false →  6 个补丁全部静默空转
                                        （不报错、不崩溃、什么都不做）
```

**你最初那句"装上了但没用"，症状和这个机制完全吻合。**

**这是一个可以避免的设计错误。** 正确做法应该是：
- 让每个补丁各自判断自己的前置条件，不要共用一个"总开关"
- 或者用多个不同的位置去置位这个开关（冗余）
- 或者干脆不做这个开关，改成检查更直接的状态

### 5.4 两个功能为什么互斥

`config.json` 里你同时写了：

```json
"AutoDodgeOnAttack": true,      // 自动闪避
"AlwaysPerfectDodge": true,     // 手动闪避必定完美
```

**但这两个永远不可能同时生效。** 反编译第 151 行：

```csharp
AlwaysPerfectDodge = !AutoDodgeOnAttack && Config_AlwaysPerfectDodge;
//                    ↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑
//                    自动闪避一开，这个就恒为 false
```

再加上热键里的互斥赋值：

```csharp
if (按 I) {
    AutoDodgeOnAttack = !AutoDodgeOnAttack;
    if (AutoDodgeOnAttack)  AlwaysPerfectDodge = false;                       // 开自动 → 关完美
    else                    AlwaysPerfectDodge = Config_AlwaysPerfectDodge;   // 关自动 → 开完美
}
```

**所以 `I` 键实际是在两种模式间切换，而不是"开关自动闪避"**：

| 模式 | 自动闪避 | 手动必定完美 |
|---|---|---|
| **I 开** | ✅ | ❌ |
| **I 关** | ❌ | ✅ |

**而且切换没有任何提示**——这也是为什么你会觉得"按了几次 I 都是在挨打"，其实那几下可能把它切到了你不想要的那个模式。

## 六、ADFix 为什么用"反射"而不是"补丁"

既然 Harmony 不可靠，我做了个辅助工具 **ADFix**，它的核心思路是：**能不用补丁就不用补丁。**

### 6.1 反射是什么

**反射 = 在运行时按名字去读/写程序里的东西。**

```csharp
// 找到那个类
Type t = FindType("PerfectDodgeMod");

// 找到名叫 IsInGame 的静态字段
FieldInfo f = t.GetField("IsInGame", BindingFlags.Static);

// 直接把它设成 true
f.SetValue(null, true);
```

**这完全不碰机器码、不装传送门、不做任何优化层面的对抗。**

### 6.2 为什么它更可靠

| | Harmony 打补丁 | 反射读写 |
|---|---|---|
| 改什么 | 方法的**机器码入口** | 字段的**内存值** |
| 会被内联影响吗 | **会**（这是死穴） | **不会**（字段没有"入口"这个概念） |
| 需要 JIT 配合吗 | 需要 | 不需要 |
| 能改逻辑吗 | 能（拦截、改写） | **不能**（只能读和写现成的数据） |

**所以 ADFix 能修好 `IsInGame` 这个单点故障（它只是改一个 bool 变量的值），但修不好"补丁被绕过"——因为触发闪避的那段逻辑本身就得靠补丁插进去。**

**一句话**：反射能改**数据**，补丁才能改**行为**。而这套 mod 的核心是改行为。

## 七、诊断方法论：怎么设计一个不会骗人的实验

这几天的排查里，有几个方法值得单独说，因为它们通用。

### 7.1 探针（Canary）

**问题**："补丁到底有没有生效？" —— 没法直接观察。

**办法**：找一个**肯定每帧都在跑**的方法，往它上面挂一个只做计数的补丁：

```csharp
public static void ProbePostfix() { ProbeHits++; }
```

**如果计数在涨 → 补丁机制是通的。如果一直是 0 → 补丁没进调用链。**

**这个探针是整晚最有价值的工具**，因为它把"mod 没反应"这个模糊现象，变成了一个可以读的数字。

### 7.2 二分法

**问题**："崩溃是 mod 造成的，还是加载器造成的？"

**办法**：把变量逐个剥离。

- 加载器 + mod → 崩
- **加载器 + 零 mod（`nomod` 档）→ 照样崩** ✓ 结论：**是加载器的问题**

**这一步省掉了后面所有的猜测。**

### 7.3 查历史，别只看当下

**问题**："崩溃是不是 mod 引起的？"

我一开始只看当天的崩溃记录，得出过错误结论。**后来去翻完整的事件日志，发现 9.5 个月前就崩过 3 次，那时什么都没装。**

**崩溃签名完全一致**（`crashhandler64.dll` + `0xc0000409`），只是 DLL 版本更新导致偏移差一点。

**结论直接反转**：崩溃是游戏本身的问题，和 mod 无关。

> **这个教训**：判断"某件事是不是新引入的"，**必须去查引入之前的历史**，
> 而不是看当前状态。我在这上面栽过一次，浪费了你几轮测试。

### 7.4 数据不完整时不要下结论

**我犯的另一个错**：拿到一份只有 60 秒、停在加载界面的日志，就推断"这批 tick 在实战中从不触发"。

后来同一批补丁在另一次会话里跑出 **1660 万次**。

> **教训**：日志的时间跨度和它覆盖的游戏阶段，必须一起看。
> "数据里没有" ≠ "事实上不存在"。

## 八、最终的结论：为什么它时灵时不灵

### 8.1 实测数据

| 会话 | 打补丁时机 | 探针命中 | 结果 |
|---|---|---|---|
| 23:53 | 启动瞬间 | **16,602,969** | ✅ 完整生效 |
| 00:02 | 启动瞬间 | 0 | ❌ |
| 00:11 | 启动瞬间 | 0 | ❌ |
| 00:14 | 启动瞬间 | 0 | ❌ |
| 00:23 | 启动瞬间 | 0 | ❌ |
| 00:34 | 启动瞬间 + 31 秒补打 | **40,976** | ✅ 完整生效 |
| 00:42 | 启动瞬间 + 31 秒补打 | 0 | ❌ |
| 00:46 | 启动瞬间 + **6 轮重打**（到 2.5 分钟） | 0 | ❌ |

**1 次成功对 6 次失败。**

### 8.2 那些数字意味着什么

成功那次 **1660 万次 / 229 秒 ≈ 每秒 7.2 万次**。

游戏按 60 帧算 → **每帧约 1200 次调用**。我挂了 379 个方法，平均每个方法每帧被调用约 3 次——
**这个数量级说明"每个敌人的每个组件每帧都在 tick"，完全合理。**

**所以这个探针是真实反映了游戏运行的，不是噪声。**

### 8.3 结论

**Harmony 补丁能不能进调用链，不受我们控制。**

- 换过两个 UE4SS 官方构建 → 无关
- 换过打补丁的时机（启动瞬间 / 31 秒 / 每 20 秒重打 6 轮）→ **无关**
- 加过重试 → **无关**
- 同样的配置、同样的时机、同样的代码 → **结果随机**

**推测机制**：JIT 内联。但**我没能证实，也没找到绕开的办法**——因为内联是运行时决定的，从外部无法干预。

**这不是你电脑的问题，也不是少做了什么。** 是这套"靠补丁改行为"的方案，在一个会做 JIT 优化的托管运行时里，天生就有这个不确定性。

## 九、名词表

| 术语 | 大白话 |
|---|---|
| **IL** | C# 编译出的"中间语言"，像带目录的原版书，能读能改 |
| **JIT** | 运行时把 IL 翻译成机器码的过程 |
| **内联** | JIT 的优化：把短方法的代码"抄"进调用方，省掉跳转 |
| **Detour / 钩子** | 在方法入口装传送门，改掉执行路径 |
| **Harmony** | 专门做 detour 的 .NET 库，mod 作者的好朋友 |
| **Prefix / Postfix** | 在方法执行前 / 后插入代码。Prefix 可以取消原方法 |
| **反射** | 运行时按名字读/写程序里的字段和方法 |
| **DLL 劫持** | 用同名冒牌 DLL 替换系统 DLL，借游戏的手把自己加载进去 |
| **KnownDLLs** | Windows 的"这些 DLL 只准从系统目录加载"名单 |
| **特征码 / AOB** | 在机器码里搜一段固定字节序列来定位函数（没名字时只能这样） |
| **探针 / Canary** | 挂一个只计数的补丁，用来判断补丁机制通不通 |
| **cvar** | 游戏的全局开关（如 `r.ScreenPercentage`），引擎启动时从 ini 读 |

## 十、现在能用的办法

**抽卡式**：启动游戏 → 玩 3 分钟 → 看 ADFix 的判定：

```powershell
Get-Content 'E:\...\Win64\CSharpLoader\Mods\ADFix\adfix.log' -Tail 12
```

| 判定 | 做法 |
|---|---|
| ✅ 补丁已进调用链 | 正常玩，自动闪避 / 窗口扩展 / `I` 键切换全部完整工作 |
| ❌ 补丁未进调用链 | 退出重开，再看一次 |

**抽到 ✅ 的那一局，mod 是完全可用的。**

**如果以后想继续**，文档里列了三个方向，其中我觉得最有希望的是：

> **绕开 Harmony，用游戏自己的 `CVar_QAEnableAutoDodge`。**
>
> 那是开发者自己写的自动闪避开关（QA = 测试用）。如果能找到**运行期**设置它的办法
> （游戏里有 GM 控制台 `BGWConsoleCommands`），就完全不需要补丁，也就没有内联问题。
>
> 我试过用配置文件在启动时设，失败了（cvar 由 C# 层注册，比引擎读 ini 的时机晚）。
> **但运行期设置是另一条路，还没试过。**
