# Harmony 的适用边界，与"我们遇到的是哪类问题"

> 回答三个问题：
> 1. Harmony 能在任何游戏上跑吗？是普适方法吗？
> 2. 我们遇到的问题属于哪一类？
> 3. 这类问题多还是少？

---

## 一、Harmony 有三个硬前提，缺一不可

**Harmony 不是"游戏修改器"，它是一个 .NET 库。** 它只能在满足这三个条件的地方工作：

| 前提 | 说明 | 不满足会怎样 |
|---|---|---|
| **① 进程里得有一个托管运行时** | Mono、.NET Framework 或 .NET Core 之一 | 没有就加载不了 Harmony |
| **② 目标必须是托管代码** | 编译成 **IL**、运行时才翻译成机器码 | 如果已经是纯机器码，没有"方法"这个概念可改 |
| **③ 补丁能写进进程内存** | 改机器码需要写权限 | 反作弊会直接拦掉甚至封号 |

**第 ② 条是关键，也是最容易被误解的。**

---

## 二、最关键的分水岭：Mono 还是 IL2CPP

**这一条决定了绝大多数 Unity 游戏能不能用 Harmony。**

Unity 游戏有两种打包方式，名字很像，机制完全不同：

```
Mono 路线：
    C# 源码  →  编译成 IL  →  打包进游戏
                              ↓
                        运行时 JIT 翻译成机器码
                              ↑
                    ✅ IL 还在！Harmony 能改

IL2CPP 路线：
    C# 源码  →  编译成 IL  →  再翻译成 C++  →  编译成机器码  →  打包进游戏
                                （打包阶段就做完了）
                              ↓
                        运行时没有 IL，只有机器码
                              ↑
                    ❌ Harmony 完全用不了
```

**IL2CPP 的出现是有原因的**：性能更好、更难被破解、跨平台更容易。**现在很多 Unity 游戏默认用 IL2CPP。**

**所以"Unity 游戏能用 Harmony"这个印象是片面的**——只对 Mono 打包的成立。

对 IL2CPP 游戏，社区工具是另一套：`Il2CppDumper` + `Il2CppInterop`（MelonLoader 那一系）。它们的原理完全不同：**先把 IL2CPP 生成的 C++ 结构逆向出来，造一份"影子"托管类，再让你调用。** 那是比 Harmony 重得多的工程。

## 三、一张表看清全局

| 游戏架构 | 逻辑层是什么 | 能用 Harmony 吗 | 社区常用工具 |
|---|---|---|---|
| **Unity（Mono）** | C# IL | ✅ 能 | BepInEx + Harmony ← **Harmony 的主场** |
| **Unity（IL2CPP）** | C++ 机器码 | ❌ 不能 | MelonLoader、Il2CppInterop |
| **UE4/UE5 纯 C++ + 蓝图** | 机器码 | ❌ 不能 | UE4SS、SDK dump + 原生钩子 |
| **纯原生引擎**（多数 3A） | 机器码 | ❌ 不能 | 特征码扫描 + detour |
| **引擎 C++ + 逻辑 C#**（**黑猴**） | C# IL | ✅ **能**（但要自己搭加载器） | **几乎没有现成工具** |

**Harmony 之所以给人"到处都能用"的印象，是因为它的名声几乎全部来自第一行。**

## 四、黑猴属于哪一类：一个罕见的组合

### 4.1 它的架构

```
┌──────────────────────────────────────────────┐
│  UE5 引擎（C++ 机器码）                        │
│  渲染、物理、动画、输入                         │
│  → b1-Win64-Shipping.exe (728 MB)            │
└──────────────────────────────────────────────┘
                    ↕  USharp 插件（桥）
┌──────────────────────────────────────────────┐
│  游戏逻辑（C# → IL）                           │
│  伤害计算、闪避判定、敌人 AI、任务系统           │
│  → b1.Managed / BtlSvr.Main 等 51 个程序集     │
│  → 打包在 exe / pak 里，磁盘上没有独立文件       │
└──────────────────────────────────────────────┘
```

**关键证据：**
- `b1\Plugins\USharp\Content` —— USharp 就是"把 C# 挂进 UE"的桥梁插件
- `MonoPosixHelper.dll` —— Mono 运行时的痕迹
- 内存里能数出 51 个托管程序集

### 4.2 为什么说它罕见

**主流 UE 游戏是"C++ + 蓝图"，没有 C# 层。** 游科选择用 C# 写逻辑层（开发效率高、热更新方便），这在技术上是个好选择，**但代价是：mod 生态几乎为零。**

因为：

| 问题 | 后果 |
|---|---|
| 逻辑在 C# 里，但没人是为这个架构做工具的 | **没有现成加载器**，得有人从零写（CSharpLoader 就是一个人写的） |
| 程序集打包在 exe/pak 里 | 常规反编译工具（ILSpy、dnSpy）**需要文件才能拖进去**，你得先在运行时从内存 dump |
| 引擎被大幅改造 | 几百个 `GS*` 自研插件，UE4SS 的特征码表里**根本没有这个游戏** |
| 游戏一更新 | 加载器、补丁目标全可能变，作者要重新逆向 |

**这就是"网上现成的 mod 不多"的结构性原因**——不是没人想做，是**工具链的每一环都得自己造**。

### 4.3 讽刺的地方

**C# 层理论上让修改变简单了**——有类名、有方法名，不像 C++ 只能靠特征码猜。

**但因为没有社区积累，这个"理论上的简单"完全没能兑现。** 你有了一本带目录的书，却发现没有别人用过这本书，连"第几页"都要自己数。

## 五、我们遇到的问题属于哪一类

### 5.1 问题类别的名字

**"插桩 vs 优化"的冲突**（Instrumentation vs. Optimization）。

换个说法：**你想在代码里插一脚，但运行时正在优化这些代码，而优化会绕过你插的那一脚。**

这两种操作天生对立：

```
插桩工具想要的：  不要动我的代码，让每次调用都经过我
运行时优化想要的：  能省则省，短方法直接抄进调用方，跳转都省掉
                    ↑ 这一抄，就把插桩抄没了
```

### 5.2 这个类别到处都是

**这不是游戏 mod 独有的问题，它在软件工程里非常经典：**

| 领域 | 工具 | 它们怎么处理这个冲突 |
|---|---|---|
| **.NET 性能分析** | Profiler API（`ICorProfilerInfo`） | **运行时主动配合**：插桩过的方法保证不被内联 |
| **Java 监控** | JVMTI / `java.lang.instrument` | JVM 支持**字节码重转换**和**去优化**（deopt） |
| **调试器** | gdb / WinDbg / VS | **附加调试器会自动关闭优化**——就是这么解决的 |
| **内核观测** | eBPF / kprobes | 内核自己处理优化过的代码和跳转桩 |
| **动态二进制插桩** | DynamoRIO、Intel Pin、Frida | 在指令级别工作，自己做代码发现和失效处理 |

**看出规律了吗？**

> **所有"可靠"的插桩方案，要么有运行时的配合，要么自己做一整套底层机制。
> "直接改方法入口"这种朴素做法，天生就是脆弱的。**

### 5.3 Harmony 的位置

**Harmony 属于最朴素的那一类**——它通过 MonoMod 在方法入口写一个跳转指令。

它**没有**运行时的配合，**没有**去优化机制，**没有**代码失效处理。它就是一个"硬改"。

**那它为什么在 Unity mod 圈名声这么好？**

因为 **Mono 的 JIT 比微软 .NET 的 JIT 保守得多**——内联没那么激进。再加上 Unity 游戏里的逻辑方法通常比"属性读取器"大，不太会被内联。

> **所以 Harmony 的可靠性，来自它常用的那个生态（Unity + Mono），
> 而不是来自这个技术本身有多稳。**

**换到一个 JIT 更激进的环境（比如 .NET Framework/Mono 的某些版本、或者有另一套代码改写系统在旁边干扰），它就会露出脆弱的一面——就是我们遇到的。**

### 5.4 为什么黑猴这个变体更棘手

**有一个我之前没充分考虑的因素：CSharpLoader 自己也在改代码。**

看它的构成：

```
CSharpLoader\
    Mono.Cecil.dll          ← IL 改写库（在内存里改游戏程序集）
    CSharpManager.bin       ← 加载器主体
    b1cs.ini → EnableJit=1  ← 有 JIT 相关的开关
```

**也就是说，这个进程里同时有两套"修改代码"的系统：**

```
CSharpLoader（Mono.Cecil）  →  在加载阶段改写 IL
Harmony（MonoMod detour）   →  在运行阶段改写机器码
```

**两者都在碰同一批方法，谁先谁后、怎么交互，没有文档、没有先例。**

**这很可能就是"同样配置结果随机"的真正来源**——不是单纯的内联，而是两套系统的时序竞争。**（这一点我没有证实，只能作为推测提出。）**

## 六、这类问题多还是少

得分三层来看：

### 第一层：问题类别 —— **非常常见**

"插桩和优化打架"是软件工程的日常。**每一个做性能监控、APM、调试器的团队都要处理它。** 这不是什么冷门难题，教科书里有标准答案（用运行时提供的插桩接口）。

### 第二层：这个失败形态 —— **不常见**

在游戏 mod 圈里，**Harmony 大部分时候是能用的**，因为大家都在 Mono 上。像我们这样"补丁全部挂载成功、却完全不在调用链上"的情况，**在公开资料里几乎找不到先例**。

这也是为什么我查不到现成答案——**不是我没找到，是这个坑可能真没人踩过并写下来。**

### 第三层：黑猴的 mod 生态 —— **极其稀少**

原因前面说了：架构罕见 + 工具链空白 + 更新会打破一切。

**一个很说明问题的数据**：我给你找的那个自动闪避 mod，是 B 站一位 UP 主"收集整合"的——**说明连作者本人都未必是原开发者，而是有人在别处做好、被搬运过来的。** 这个圈子的规模由此可见。

## 七、如果要做"正确"的版本，该怎么做

假如不计成本，符合工程规范的做法是：

### 方案：用 .NET Profiling API 而不是 Harmony

```
普通做法（我们现在这样）：
    游戏启动 → 加载器注入 → Harmony 硬改机器码 → 和 JIT 打架

正确做法：
    游戏启动时通过环境变量挂上 Profiler
        ↓
    运行时主动回调你的代码："我要编译这个方法了"
        ↓
    你用官方接口 SetILFunctionBody 替换 IL
        ↓
    ✅ 运行时保证：这个方法不会被内联，你的插桩一定生效
```

**这是微软官方支持的插桩方式**，性能分析器、APM 工具都用它。**运行时是配合你的，不是和你抢。**

### 代价

| 项 | Harmony | Profiling API |
|---|---|---|
| 接入方式 | 一个 DLL + 几行代码 | 需要 COM 注册、需要进程启动时就挂上 |
| 开发难度 | 低 | **高**（要写 COM 组件、处理回调） |
| 可靠性 | **看运气** | 运行时保证 |
| 社区先例 | 一堆 | **游戏 mod 领域几乎没有** |
| 能否中途启用 | 能 | **不能**，必须进程启动时挂 |

**最后一行是致命的**：Profiling API 必须在进程启动前通过环境变量指定，**没法"进了游戏再开"**。对 mod 来说这意味着改变用户的启动方式（要用一个启动器）。

**所以这不是"能做但不做"，而是"投入产出比不划算"**——为了一个自动闪避，要重写整个加载层。

## 八、一句话总结

| 问题 | 答案 |
|---|---|
| Harmony 普适吗？ | **不普适。** 需要托管运行时 + IL 还在 + 能写内存。IL2CPP 和纯 C++ 游戏都用不了 |
| 是普适方法吗？ | **在 Mono 生态里是事实标准**；但技术上它是"朴素硬改"，可靠性靠的是环境友好，不是技术可靠 |
| 我们遇到的是哪类问题？ | **插桩 vs 优化**的冲突。经典问题类别，但**这个具体形态（补丁全部成功却完全不在调用链上）在游戏 mod 领域很罕见** |
| 这类问题多还是少？ | **类别常见、形态罕见、黑猴生态极稀少** |
| 有正确做法吗？ | 有（.NET Profiling API），但**门槛高、必须启动时挂载，对 mod 场景不划算** |
| 那我该怎么办？ | **抽卡**：启动 → 等 3 分钟看 ADFix 判定 → ❌ 就重开。抽到 ✅ 那局完全可用 |

## 附：这件事真正的价值

**不是做出了 mod，是把一个没人写过的坑记录下来了。**

几天里确认下来的、有实测数据支撑的事实：

1. **UE4SS 与黑猴不兼容** —— dump 实证 `UE4SS.dll` 空指针崩溃，`nomod` 档零 mod 照样崩
2. **UE4SS 官方配置里没有黑猴** —— 14 个定制配置，一个都不是
3. **游戏崩溃是预存的** —— 9.5 个月前就崩过 3 次，签名完全一致，那时什么都没装
4. **Harmony 补丁投递在本机随机** —— 1 次成功对 6 次失败，同样配置同样时机
5. **`IsInGame` 单点故障** —— 反编译确认全文唯一置位处落在一个可能不跑的 tick 里
6. **那个 mod 的两个功能天生互斥** —— 反编译第 151 行的 `!AutoDodgeOnAttack`
7. **CSharpLoader 的控制台能当调试器用** —— `Console=1` 打开了它的日志输出

**这些都能直接拿去给 mod 作者提 issue，也能让下一个想踩这个坑的人少走几天弯路。**
