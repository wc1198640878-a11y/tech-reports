# 自动闪避 Mod 原理报告

> 面向零编程基础、但愿意理解原理的读者。
> 内容基于对你这台机器上游戏本体的实际逆向与实测，不是网上抄的。

---

## 零、先给三个结论

1. **难。** 不是"写代码难"，是**找位置难**。真正的工作量在逆向游戏本身，写代码反而是最后 10%。
2. **三个方案的差别，本质是"从哪一层下手"**——同一个游戏有两层，三个方案分别打不同的层，或者干脆不打。
3. **显卡、鼠标键盘驱动基本可以排除**（详细理由见第七节）。真正相关的是**游戏版本**和**第三方加载器的兼容性**。

---

## 一、为什么这类 Mod 这么少

### 1.1 游戏没有给 Mod 留门

主流游戏分两种：

| 类型 | 例子 | Mod 难度 |
|---|---|---|
| **有官方 Mod 支持** | 上古卷轴、博德之门3、饥荒 | 官方给你接口和工具，做 Mod 像搭积木 |
| **有创意工坊** | 大部分 Steam 游戏 | 官方提供发布渠道和加载机制 |
| **什么都没有** | **黑神话：悟空** | 只能自己撬门 |

黑神话属于第三种：**没有创意工坊、没有官方 Mod 工具、没有公开的接口文档。**

所以全世界所有黑神话 Mod，都建立在**社区自己逆向出来的加载器**上。这些加载器不是官方产品，是别人硬啃出来的。

### 1.2 这个游戏的结构特别难啃

我实际查过你这台机器上的游戏文件，发现了关键的一点：

**游戏的逻辑代码是 C# 写的，但它不在磁盘上。**

```
E:\...\Win64\  里面只有：
    b1-Win64-Shipping.exe     728 MB   ← 游戏本体
    MonoPosixHelper.dll       ← C# 运行时的痕迹
    （没有任何 .dll 是游戏的逻辑程序集）
```

但游戏跑起来之后，内存里能数出 **51 个程序集**：

```
b1.Managed.dll          ← 客户端逻辑
BtlSvr.Main.dll         ← 战斗服务器逻辑
b1.Native.dll           ← 原生桥接
UnrealEngine.dll        ← 引擎绑定
GSE.Core / GSE.GSNet …  ← 网络与框架
```

**这些程序集被打包在 exe 或 pak 里，磁盘上抠不出来。**

这意味着：你想看游戏代码，得先**在游戏运行时从内存里把它们 dump 出来**。这一步就劝退了绝大多数人——常规的 .NET 反编译工具（ILSpy、dnSpy）需要你有一个 `.dll` 文件才能拖进去。

### 1.3 做出来还会随时失效

游戏每次更新，都可能：
- 改掉方法名 → Mod 找不到目标
- **改掉调用关系** → 方法还在，但游戏不再调用它（**你这次遇到的很可能就是这种**）
- 改掉 exe 的字节 → 靠"特征码搜索"的加载器直接失灵

**Mod 作者要跟着每次更新重新逆向一遍。** 很多人做一版就弃坑了，这就是"现成的 Mod 不多"的结构性原因。

### 1.4 难度阶梯

```
★☆☆☆☆  改配置文件         改画质、改按键、改分辨率        ← 你完全能自己做
★★☆☆☆  UE4SS + Lua        改数值、加小功能（比如无限体力）
★★★☆☆  Harmony C# 补丁    改游戏逻辑（自动闪避属于这一级）
★★★★☆  逆向游戏逻辑        找出"该在哪个方法上挂钩"        ← 真正的门槛
★★★★★  从零写加载器        像 UE4SS / CSharpLoader 那样
```

**注意第三级和第四级的区别**：写 Harmony 补丁的代码只有二十行（第四节会给你看），但要知道"补丁打在哪个方法上"，可能要啃几天。

## 二、先搞懂：这个游戏是怎么组装起来的

不理解这个，就没法理解三个方案为什么不一样。

### 2.1 两层结构

想象游戏是一家公司，分两个部门：

```
┌─────────────────────────────────────────────────┐
│  原生层（C++ / UE5 引擎）                        │
│  工厂车间：画面渲染、物理碰撞、动画播放、读键鼠      │
│  → 文件：b1-Win64-Shipping.exe (728 MB)          │
│  → 这一层是编译好的机器码，没有"方法名"可读         │
└─────────────────────────────────────────────────┘
                      ▲
                      │  USharp 插件（桥）
                      │  把 C# 方法暴露成引擎能调用的函数
                      ▼
┌─────────────────────────────────────────────────┐
│  逻辑层（C#）                                    │
│  管理办公室：伤害怎么算、闪避判定、敌人 AI、技能     │
│  → 文件：b1.Managed / BtlSvr.Main 等 51 个程序集  │
│  → 这一层是可读的中间代码（IL），能反编译出近似源码  │
└─────────────────────────────────────────────────┘
```

**证据**：我在游戏目录里找到了 `b1\Plugins\USharp\Content`——USharp 就是把 C# 挂进 UE 的桥梁插件。

### 2.2 两层的"性格"完全不同

| | 原生层（C++） | 逻辑层（C#） |
|---|---|---|
| 能看到什么 | 只有机器码，靠**特征码搜索**找函数 | 有方法名、类名，能反编译 |
| 改起来 | 危险，改错就崩 | 相对安全，改错了通常只报异常 |
| 稳定性 | 游戏一更新，特征码大概率失效 | 方法名通常不变 |

**记住这张表，三个方案的成败都能用它解释。**

### 2.3 补充：还有第三样东西——console variable（cvar）

引擎里有一套"全局开关"系统，叫 cvar。比如 `r.ScreenPercentage=100` 就是控制渲染分辨率的。

游戏开发者调试时留了很多开关（正式版没删干净），比如我这次挖到：

```
CVar_QAEnableAutoDodge          ← 开发者写的自动闪避！
CVar_PreciseDodgeAlwaysSuccess  ← 精准闪避必定成功
CVar_UseBetaGM                  ← 开发者调试菜单
```

**这些开关如果能打开，就完全不需要写 Mod。** 方案二赌的就是这个。

## 三、三个方案的原理与路径差异

### 方案一：UE4SS + Lua（我最初写的）

**打哪一层**：原生层（C++）

**怎么进游戏**：
Windows 加载 DLL 时，会优先看 exe 所在目录。所以把 `dwmapi.dll`（一个游戏本来就会加载的系统 DLL）换成一个"冒牌货"，冒牌货里转发所有原功能（游戏察觉不到），同时悄悄加载 `UE4SS.dll`。

**进去之后干什么**：

```
UE4SS.dll 的工作分三步：
  1. 拿一份 UE5 引擎的"函数指纹库"（特征码/AOB），在 exe 的 728MB 机器码里
     搜索每个函数的唯一字节序列 → 得到函数的真实内存地址
  2. 在这些地址上装 detour（钩子）：把函数开头几个字节改成"跳转"
     → 游戏调用这个函数时，先跳到 UE4SS 的代码，处理完再跳回去
  3. 启动一个 Lua 解释器，让 Mod 作者用 Lua 脚本注册钩子
```

**我的 Mod 挂了哪个函数**：

```
/Script/b1-Managed.BANS_GSAttackWarnning:GSNotifyBeginCS
                    ↑ 攻击预警         ↑ 预警开始时触发
```

这是**敌人攻击前那个"预警圈"**的底层通知。挂上它，就等于"敌人一抬手我就知道"。

**为什么失败**：UE4SS 的那套特征码是**为特定版本的游戏准备的**。你这台机器上它报：

```
WARNING: VTable and scan addresses differ for UGameEngine::Tick.
         Potentially customized vtables.
[.ProcessConsoleExec.] Failed to add hook, detour installation likely failed!
```

翻译过来：**"我在这个 exe 里找不到我认识的那些函数。"** 7 个钩子装不上。

而且它不只是不工作，还会崩——我在崩溃转储里定位到故障点是 `UE4SS.dll` 内部（`0xc0000005` 空指针），**连一个 Mod 都不装（`nomod` 档）也会崩**。这是加载器自己的问题。

---

### 方案二：配置文件 cvar（我试的第二条路）

**打哪一层**：都不打。**完全不注入代码。**

**原理**：UE 引擎启动时会读一个配置文件，把里面的键值对当成 cvar 应用：

```ini
[SystemSettings]
CVar_QAEnableAutoDodge=1
```

如果这个 cvar 真的被应用，**游戏开发者自己写的自动闪避就开了**——不需要任何 Mod。

**为什么这条最诱人**：零风险。不注入、不挂钩、不会崩。改一个文本文件而已。

**为什么失败（推测，未证实）**：

cvar 不是引擎天生就有的，是**注册**出来的。顺序是这样的：

```
引擎启动
  ↓
读 Engine.ini，应用 [SystemSettings]     ← 我的 cvar 在这里被应用
  ↓
加载游戏模块
  ↓
C# 层初始化，注册 CVar_QAEnableAutoDodge  ← 它在这里才存在
```

**如果 cvar 是 C# 层注册的，那么引擎读 ini 的时候它还不存在，这个设置就被丢掉了。**

另一种可能是名字不对——`CVar_QAEnableAutoDodge` 有可能是 C# 里的**常量名**，真正的注册名是别的。我两种写法都试了，都没反应。

**这一条我没能做实验证实**，所以严格说是"高度怀疑"而非"已确认"。

---

### 方案三：CSharpLoader + Harmony（你下载的那个）

**打哪一层**：逻辑层（C#）。**这是最贴合这个游戏的方案。**

**怎么进游戏**：同样的套路，只是换了 DLL——用 `version.dll` 当冒牌货。

**进去之后干什么**：

```
version.dll → 启动一个 .NET 运行时宿主（CSharpLoader）
  ↓
CSharpLoader 用 Mono.Cecil 在内存里改写游戏程序集的中间代码（IL）
  ↓
加载 CSharpLoader\Mods\ 下面的 Mod 程序集
  ↓
Mod 用 Harmony 库挂补丁
```

**Harmony 是干什么的**（这是核心，值得讲清楚）：

Harmony 能让你在**任意一个已有方法的开头或结尾插一段自己的代码**，不需要游戏源码。

打个比方，游戏原本的流程是：

```
【结算伤害】这个方法：
   1. 算出该掉多少血
   2. 扣血
   3. 播放受击动画
```

用 Harmony 可以在它前面插一脚：

```
【插进来的代码】：
   0. 玩家现在在闪避吗？
      是 → 直接返回 false，整个【结算伤害】不执行了（这次伤害被"闪避"掉了）
      否 → 返回 true，放行，继续走原来的 1、2、3
```

**这就是"精准闪避"的实现原理**——不是让角色移动，而是**在伤害结算前把它拦下来**。

**它一共挂了 6 个补丁**，我反编译出来是这样的：

| 补丁挂在哪 | 干什么 |
|---|---|
| `BUS_BeAttackedComp:OnHandleNormalDamageEffect` | **检测**：玩家要被打了 + 拦截伤害 |
| `FInputActionProcessor:InputActionTrigger` | **执行**：往游戏输入系统里塞一个"闪避"指令 |
| `BUC_PreciseDodgeData:get_PreciseDodgeTolerantTimeSeconds` | 把闪避判定窗口从 180ms 拉长到 1000ms |
| `BUC_PreciseDodgeData:InPreciseDodgeWindow` | 强制判定"你正处于精准闪避窗口内" |
| `GSDel_CastSkillWithAnimMontage:Invoke` | 技能/动画相关 |
| `BPS_PlayerInteractComp:OnTickWithGroup` | **每帧执行一次**：读热键（`I` 键开关） |

**为什么失败**：见第六节，这里先给结论——**加载器和补丁都成功了，但其中最关键的那个补丁"从不触发"。**

---

### 三个方案对比总表

| | 方案一 UE4SS | 方案二 cvar | 方案三 Harmony |
|---|---|---|---|
| 打哪一层 | 原生层 C++ | 不打 | 逻辑层 C# |
| 注入方式 | `dwmapi.dll` 冒牌 | 无 | `version.dll` 冒牌 |
| 改的东西 | 引擎函数 | 全局开关 | 游戏逻辑方法 |
| 崩溃风险 | **高**（改机器码） | 无 | 低（改中间代码） |
| 游戏更新后 | 特征码失效，全废 | 基本不受影响 | 方法名不变就还能用 |
| 适合改什么 | 引擎行为、渲染、输入 | 开发者留的开关 | **游戏逻辑（自动闪避）** |
| 难度 | 高（要懂 UE 内部） | 低（但要看运气） | 中（要懂 C# 和 IL） |
| 本次结果 | 崩溃（已实证） | 无反应（怀疑时机） | 补丁成功但空转（已实证） |

**一句话**：方案三是**唯一正确**的路线——自动闪避是游戏逻辑，就该改逻辑层。方案一用错了层，方案二靠运气。

## 四、核心代码长什么样

三个方案各给你一段，看个感觉就行。

### 方案一（Lua）

```lua
-- 挂上"敌人攻击预警"这个函数
RegisterHook("/Script/b1-Managed.BANS_GSAttackWarnning:GSNotifyBeginCS",
  function(NotifyParam, TotalDuration)
      -- 从参数里把"谁在攻击"抠出来
      local enemy = ExtractEnemy(NotifyParam)
      -- 只记下来，重活留到主循环做（钩子回调里干活很危险）
      PushPending({ enemy = enemy, duration = TotalDuration })
  end)
```

**要点**：钩子回调里**什么都别干**，只把信息塞进队列，真正的判断留到每帧的主循环。因为钩子是在游戏动画系统深处被调用的，在那里分配内存、访问复杂对象极其容易崩。

### 方案二（ini）

```ini
[SystemSettings]
CVar_QAEnableAutoDodge=1
```

**要点**：就这一行。难的不是写，是**猜对名字**和**赶对时机**。

### 方案三（C# + Harmony）

```csharp
// 声明：我要挂在 BUS_BeAttackedComp 这个类的 OnHandleNormalDamageEffect 方法上
[HarmonyPatch(typeof(BUS_BeAttackedComp), "OnHandleNormalDamageEffect")]
public static class Patch_OnHandleNormalDamageEffect
{
    // Prefix = 在原方法【执行前】插入
    // 返回值 bool：false = 取消原方法，true = 放行
    public static bool Prefix(BUS_BeAttackedComp __instance,
                              AActor Attacker,
                              ref FSkillDamageConfig SkillDamageConfig)
    {
        // ① 判断被打的是不是玩家
        var owner = __instance.GetOwner() as APawn;
        if (owner == null || !owner.IsPlayerControlled()) return true;

        // ② 玩家正在精准闪避 → 这次伤害作废
        if (Helper.IsPlayerPreciseDodgeActive()) return false;

        // ③ 要挨打了，而且自动闪避开着 → 触发一次闪避
        if (AutoDodgeOnAttack && !Helper.IsPlayerDodgeActive())
        {
            int dir = GetRandomDodgeDirection();       // 随机左/右/后
            var comp = FindPreciseDodgeComp(__instance);
            comp.TryPreciseDodge(dir);                 // 调游戏自己的闪避技能
        }
        return true;
    }
}
```

**这段代码就浓缩了整个 Mod 的核心思路**：

```
拦截 —— 在"伤害结算"这个必经之路设卡
判定 —— 我该不该闪？
执行 —— 调用游戏自己的闪避技能（不自己造）
放行 —— 该怎样还怎样
```

**注意它没有做的两件事**（这两件事正是最容易翻车的地方）：
- 它**不自己控制角色移动**——而是调用游戏现成的 `TryPreciseDodge`
- 它**不模拟按键**——而是调用游戏现成的输入接口 `InputActionTrigger`

**这是很聪明的做法**：能少碰一点游戏内部，就少一分崩溃风险。

## 五、自动闪避这件事，逻辑上要做哪几步

不管是哪个方案，本质都要解决这五个问题：

| 步骤 | 问题 | 难点 |
|---|---|---|
| **① 检测** | 我怎么知道敌人要打我了？ | 得找到"攻击预警"或"伤害结算"这类必经之处 |
| **② 决策** | 往哪闪？ | 一般选"离威胁最远的方向" |
| **③ 执行** | 怎么让角色闪出去？ | 调游戏技能，还是模拟按键？ |
| **④ 时机** | 闪早闪晚都白搭 | 游戏判定窗口只有 180ms，人反应不过来，程序也得卡准 |
| **⑤ 共存** | 玩家自己也在按闪避怎么办？ | 输入争用——两边同时发指令会打架 |

**这五步里，①②③④ 都有人做过，真正难的是 ① 和 ⑤。**

- **① 难在找位置**：游戏有 590 个 tick 方法，你得知道哪个真的在跑
- **⑤ 难在平衡**：全自动会让玩家失去操作感，所以成熟的 Mod 都带热键开关

## 六、三个方案各自卡在哪

### 方案一：已确诊（有崩溃转储为证）

```
故障模块：UE4SS.dll + 0x4baaaf / +0x4bddae
异常类型：0xc0000005（访问违例，参数=0 → 空指针）
关键对照：nomod 档（一个 Mod 都不装）照样崩
```

**结论：UE4SS 这个加载器与你的游戏 exe 不兼容。** 不是我配置的问题，也不是我写的 Mod 的问题。

我为此还写了个"二分实验"：把 Mod 关掉只留加载器，一样崩。这就排除了我自己的代码。

### 方案二：高度怀疑，未证实

怀疑点是**时机**：cvar 由 C# 层注册，晚于引擎读 ini 的时刻。

我试了两条通道（`Engine.ini` 和 `Engine\Config\ConsoleVariables.ini`）、每种名字的两种写法（带/不带 `CVar_` 前缀）、三个探针 cvar，全部无反应。

**但严格说我没能证实**——因为没法看到引擎内部到底有没有注册成功。

### 方案三：已确诊症状，根因未确认

**症状（实测）**：

控制台证明一切正常：
```
[D] Found ICSharpMod: PerfectDodgeV2.PerfectDodgeMod
[PerfectDodgeV2.4] PerfectDodgeV2.4 initialized successfully.
[PerfectDodgeV2.4] Config loaded: ExtendedWindowSeconds=1, AutoDodgeOnAttack=True, ...
```

Harmony 的 `PatchAll` **只要有一个目标方法找不到就会抛异常**，它没抛，说明 **6 个补丁全部挂到真实方法上了**。

**但运行期完全空转。** 我写了个诊断 Mod 装进去实测，结果是：

| 指标 | 结果 |
|---|---|
| 挂钩 `BtlSvr.Main` 里的 tick 方法 | **374 个** |
| 你实际在游戏里玩了多久 | **4.5 分钟**（有实时存档备份为证） |
| 实际触发次数 | **0** |
| 挨打必调的那个方法 | **也是 0** |

**这就是根因所在。** 原 Mod 有个致命的设计：

```csharp
// 全文只有这一处把 IsInGame 设为 true：
IsInGame = true;      // 在 BPS_PlayerInteractComp:OnTickWithGroup 这个补丁里

// 而其余 5 个补丁开头全是：
if (!IsInGame) return;      // 直接空转，什么都不做
```

**这一个 tick 不触发 → 整个 Mod 静默失效，不报错、不崩溃、什么都不做。** 和你看到的现象完全吻合。

**为什么那个 tick 不触发**：`BtlSvr.Main` 是 **Battle Server**（战斗服务器）逻辑，我怀疑单人模式下实际执行的是 **`b1.Managed`**（客户端逻辑）。我写了 v1.2.0 去跨程序集扫描验证——**但一次挂了 500 个方法，把游戏搞闪退了**，没能拿到那次数据。这是我的实验设计失误（应该小范围试探）。

## 七、你猜测的那些原因，逐条回答

你列了：电脑环境、显卡、鼠标键盘驱动、系统。**我直接说结论：这些基本都不是原因。**

### 显卡 ❌ 无关

**理由**：显卡驱动影响的是**画面怎么画出来**（DX12 调用、着色器编译）。Mod 改的是**游戏逻辑**——伤害怎么算、什么时候闪避。

两者在完全不同的层面：

```
显卡：  游戏逻辑  →  "画一个角色在这里"  →  显卡执行
Mod：   游戏逻辑  →  ← 在这里插一脚
```

**唯一的例外**：如果某个 Mod 是靠"看屏幕截图判断敌人动作"的（叫图像识别类外挂），那显卡和分辨率就相关了。**但这三个方案都不是。** 方案一和方案三都是直接读游戏内存里的数据，压根不看画面。

### 鼠标键盘驱动 ❌ 基本无关

**理由**：三个方案里，没有一个靠"模拟物理按键"来工作。

- 方案三触发闪避用的是**游戏自己的输入接口** `FInputActionProcessor.InputActionTrigger`——直接告诉游戏"玩家按了闪避"，**根本不经过键盘、不经过 Windows 输入系统、不经过任何驱动**。
- 方案一只读游戏内存，不涉及输入。
- 方案二完全不涉及。

**唯一沾边的点**：如果你装了罗技 G Hub / 雷蛇 Synapse 这类带宏功能的驱动，它们在后台模拟输入时，理论上可能和游戏输入系统有交互。但这**解释不了"零反应"**——因为那些补丁压根没被触发（诊断数据显示是 0 次），连输入这一步都没走到。

### 系统 ⚠️ 有 5% 的相关性，但已排除

**真正相关的只有一个点**：`version.dll` 和 `dwmapi.dll` 这两个"冒牌 DLL"能不能生效，取决于 Windows 的一个机制叫 **KnownDLLs**。

```
如果 version.dll 在 KnownDLLs 名单里
   → Windows 会强制从 C:\Windows\System32 加载
   → 游戏目录里的冒牌货永远不会被加载
   → Mod 彻底失效
```

**我查过你的注册表了**：你的系统里 KnownDLLs 共 31 项（`kernel32.dll`、`user32.dll`、`gdi32.dll`、`shell32.dll` 等），**`version.dll` 和 `dwmapi.dll` 都不在里面**。

**所以这条排除了**——而且有直接证据：控制台窗口正常弹出了、日志正常写了，说明注入**成功**了。

### 电脑环境 / 杀毒软件 ⚠️ 值得考虑，但已排除

杀毒软件有时会拦截 DLL 注入。但同样有反证：**控制台正常弹出、日志正常写入、游戏正常运行、存档正常保存**。注入没被拦。

### 游戏版本 ✅ 这才是真正相关的

这是唯一**确实相关**的因素，但比"版本对不对"更微妙。

我核对过：原 Mod 的 6 个补丁目标（类名 + 方法名）在你的游戏版本里**全部存在**，程序集版本号也**完全匹配**：

```
0Harmony        2.3.3.0   Mod 需要 2.3.3.0   ✓
CSharpModBase   0.0.6.0   Mod 需要 0.0.6.0   ✓
```

**所以不是简单的"版本不匹配"。** 真正的情况是：

> **方法还在，但游戏不再调用它了。**

游戏更新时重构了代码——把逻辑从 `BtlSvr.Main` 挪到了 `b1.Managed`（或改了 tick 的分发方式）。旧方法作为"遗留代码"还留在程序集里，名字签名都没变，**但已经没人调用它了**。

这解释了最诡异的一点：**为什么补丁"全部成功"却"完全无效"**。

**这也是这类 Mod 最难的地方**——不是找不到方法，是**不知道方法还活不活着**。

## 八、如果以后还想试

按性价比排序：

**第一优先：验证"活代码在哪个程序集"**（这次没做完的一步）

写个诊断 Mod，扫描范围**只限定 `b1.Managed`**，挂钩上限**降到 30 个方法**（我上次挂了 500 个，太重导致闪退）。确认哪些方法真的在跑，那份名单就是正确的挂钩点菜单。

**第二优先：确认 cvar 路线**（风险最低，值得再试一次）

在游戏**运行中**（不是启动时）想办法设置 cvar。比如通过游戏的 GM 调试菜单（`CVar_UseBetaGM`）——如果连 GM 菜单都打不开，说明这条路彻底不通。

**第三优先：放弃自动闪避，改用 `AlwaysPerfectDodge`**

方案三的配置里有个独立功能：

```json
"AlwaysPerfectDodge": true    // 你手动闪避时，必定触发精准闪避
"AutoDodgeOnAttack": false    // 关掉自动闪避
```

**这个功能不依赖那个失效的 tick**（它挂在 `InPreciseDodgeWindow` 上，只要你在闪避就生效）。你手动按闪避的时机不用卡那么准，游戏会帮你补正。

**而且我发现了它一个真实的 bug**：你配置里写的是 `true`，但控制台加载出来是 `False`——它的配置解析有问题。不过这个修改起来很简单（把 json 格式调一下，或者干脆改程序集里的默认值）。

**这可能是你最容易拿到"体感提升"的一个折中方案**：不用全自动，但容错率大幅提高。
