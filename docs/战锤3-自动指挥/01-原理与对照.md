# 全面战争：战锤3 自动指挥 Mod —— 原理与对照

> 这是我之前给这个工作区写的另一个项目。它和黑猴那个自动闪避 mod **恰好构成完美对照**：
>
> | | 黑猴 | 战锤3 |
> |---|---|---|
> | 接入方式 | DLL 注入 + 机器码补丁 | **把文件丢进游戏目录** |
> | 可靠性 | 随机（约 1/6 次成功） | **确定性** |
> | 生态 | 空白 | **成熟** |
>
> **原因只有一个：战锤3 给了官方脚本接口，黑猴没有。**

---

## 零、这个 mod 是干什么的

**《战锤3：全面战争》单机战斗内全自动指挥**：进战斗即接管玩家全军，由"游戏原生战斗 AI 打底 + 自写 Lua 战术规则层"指挥，目标不是打赢，而是**以最小伤亡打赢**。

**注意这个目标的措辞**——"以最小伤亡"不是"能赢就行"。这决定了整个架构：

> 原生 AI 会赢，但它会**拿人命换**。所以要在它上面加一层"爱惜兵力"的规则。

---

## 一、最重要的一点：它用的是游戏官方给的接口

**这不是"绕过游戏"，而是"游戏请你来写"。**

全面战争系列从很早就提供 **Lua 脚本沙箱**，战斗和战役都开放了脚本 API：

```
游戏 data 目录
    └─ 放一个 .pack 文件（本质是个压缩包）
            └─ script/battle/mod/*.lua   ← 游戏启动战斗时自动加载并执行
```

**对比一下三种接入方式：**

| 方式 | 战锤3 | 黑猴 |
|---|---|---|
| **官方脚本接口** | ✅ **有** | ❌ 没有 |
| **需要注入 DLL 吗** | ❌ 不需要 | ✅ 必须 |
| **需要改机器码吗** | ❌ 不需要 | ✅ 必须 |
| **崩溃风险** | **几乎为零**（沙箱内） | 高 |
| **能查官方文档吗** | ✅ 有 | ❌ 得反编译 |

**这是生态里最重要的一环。** 有官方接口的游戏，mod 是"填表格"；没有的，mod 是"撬锁"。

**而我上一份报告里给的决策流程，第一条就是"优先选游戏自带的 mod 接口"——这个项目就是那条路的实例。**

---

## 二、三层指挥架构（核心设计）

```
┌──────────────────────────────────────────────────────┐
│  层2  主脚本 wh3_auto_commander.lua                    │
│       职能：托管管道、阶段调度、打补丁、战损统计          │
│       ↓ 把全军交给 ↓                                   │
├──────────────────────────────────────────────────────┤
│  层0  原生战斗 AI（script_ai_planner）                  │
│       职能：半自主作战——自己找目标、自己接敌、自己放技能   │
│       ↑ 规则层从中"借用"单位，用完还回去 ↑               │
├──────────────────────────────────────────────────────┤
│  层1  规则覆盖层 ac_tactics.lua                        │
│       职能：每 1.7 秒轮询一次，只在收益明确的时机干预      │
│       预备队轮换 / 骑兵循环冲锋 / 飞行纪律 / 炮兵反制 /   │
│       两翼包夹 / 攻城轻推 / 胜利追击                     │
└──────────────────────────────────────────────────────┘
```

### 2.1 为什么这么分层：不要重造 AI

**最容易犯的错是"自己写一套战斗 AI"。** 那是几千小时的工程量，而且做不过人家。

**正确的做法是：让游戏的 AI 干活，你只在它做得不好的地方插手。**

原话写在设计文档里：

> **核心原则：只在收益明确的时机干预，其余时间让原生 AI 发挥。**

### 2.2 干预的具体机制："收编 → 直控 → 交还"

```
① remove_sunits   把这个单位从 planner 里摘出来（AI 不再管它）
② 用 unitcontroller 下达精确指令（goto / attack / halt）
③ add_sunits      用完还回去（AI 重新接管）
```

**而且每次干预必须设冷却。** 原因写在文档里：

> 防止脚本与原生 AI 抢控制权造成**单位抽搐**。

**这是这个项目的核心难点，也是一个通用问题：**

> **两个"大脑"同时指挥同一支部队，部队就会抽搐。**
>
> 这和黑猴项目里的"输入争用"（玩家手动操作 vs 自动闪避同时发指令）
> **是同一个问题类别**——只不过那边争的是输入，这边争的是控制权。

### 2.3 各组的职责划分

```lua
line       -- 正面接战线（is_infantry 且非远程）
anti_cav   -- 两翼反骑
ranged     -- 输出主力，受保护
artillery  -- 高价值输出，绝不进近战
cav        -- 机动组：包抄 / 救火 / 追溃
flyers     -- 偷后排 / 支援
lords      -- 光环走位
reserve    -- line 中按 strategic_value 排名的次强 15%，用于轮换
```

**"预备队 = 次强 15%"这种量化规则，就是规则层的价值所在。** 原生 AI 不会这么精细地保命。

## 三、技术要点逐个拆解

### 3.1 自动加载机制

```lua
-- 路径：data/script/battle/mod/wh3_auto_commander.lua
-- 游戏启动战斗时自动执行，不需要任何注册代码

local MOD = "AUTOCOMMANDER";
local function log(msg) bm:out(MOD .. ": " .. tostring(msg)); end;
```

**`bm` = battle_manager**，是游戏在加载 mod 脚本之前就已经建好的全局对象。

**这就是"官方接口"的具体样子**：你不用找函数地址，游戏直接把对象递给你。

### 3.2 释放盾 —— Lua 层面的"猴子补丁"

**这是整个项目最精彩的一处。**

**问题**：CA 的包装函数（`attack_force` / `move_to_position` 等）内部会调用 `ensure_units_are_released`，把军队控制权**还给玩家**。结果是 AI 刚接手就被踢出来 → **全军僵死**。

**解法**：在 Lua 里直接把那个函数换掉：

```lua
-- 先留住原函数
local original_ensure_units_are_released = script_ai_planner.ensure_units_are_released;

-- 然后用一个新函数顶替它
script_ai_planner.ensure_units_are_released = function(self)

    -- 盾生效条件：战斗阶段（Deployed）全程压制
    if current_phase == "Deployed" then
        return;            -- ← 什么都不做，"夺权"就被挡住了
    end;

    -- 其余情况照常执行（原逻辑）
    for i = 1, #self.sunit_list do
        local su = self.sunit_list[i];
        if su and su.uc then su.uc:release_control(); end;
    end;
end;
```

**这个手法在概念上和 Harmony 完全一样：**

| | Harmony（黑猴） | Lua 猴子补丁（战锤3） |
|---|---|---|
| 做什么 | 替换函数的**机器码入口** | 替换表里的**函数引用** |
| 可靠性 | **随机**（JIT 内联会绕过） | **确定性**（查表必然命中） |
| 出错的后果 | 静默失效 | 静默失效（但至少是确定的） |

**同样的思路，可靠性天差地别——因为一层是动态语言的表查找，一层是编译后的机器码。**

> **这就是"选对层"的价值。**

### 3.3 轮询而非事件

```lua
poll_interval_ms = 1700,   -- 单位收编轮询
diag_interval_ms = 5000,   -- 控制权诊断日志
```

游戏有战斗事件系统，但**官方推荐轮询**（`bm:repeat_callback`）。原因很简单：**事件会漏，轮询不会**——只要你的判断条件是"当前状态"，轮询天然幂等；而事件驱动的逻辑一旦漏一个事件，状态机就卡死了。

**规则层也是同一个模式**：每 1.7 秒扫一遍战场，该干预的干预，不该动的什么都不做。

### 3.4 阶段回调

```lua
bm:register_phase_change_callback("Deployed", fn);
-- 阶段：Deployment → Deployed → VictoryCountdown → Complete
```

**"进战斗即自动托管"靠的就是这个**——`Deployed` 阶段一到，开始收编全军。

而且这些阶段名是**可观测的**：实测日志里出现过完整序列
`loaded ok → Deployment → Deployed → VictoryCountdown → Complete`，
**这一条日志就验证了"mod 加载 → 脚本执行 → 阶段回调 → 日志输出"整条链路。**

> **这和黑猴那个"探针"是同一个思路**：先证明链路通，再谈功能。

## 四、踩过的坑（这些坑很经典）

### 4.1 Lua 的 upvalue 陷阱 —— **和黑猴项目撞了同一个坑！**

**症状**：释放盾失效，30 秒后全军控制权还给玩家。

**原因**：

```lua
-- 错误顺序
script_ai_planner.ensure_units_are_released = function(self)
    if current_phase == "Deployed" then   -- ← 这里的 current_phase 解析成【全局变量】
        return;
    end;
end;

local current_phase = "";                 -- ← 太晚了！
```

**Lua 的 `local` 声明，只在它所在的那一行之后才可见。** 闭包定义在 `local` 之前，那个名字就不会绑定到局部变量，而是去找全局——**全局永远是 nil，盾永远不生效。**

修法是**把声明提到补丁之前**，并加一条 lint 断言这个顺序。

> ### 🔑 这和黑猴那个项目是**完全同一类 bug**
>
> 我在黑猴的 Lua mod 里也踩了：`local DrainPending` 定义在 `OnTick` **之后**，
> 于是 `OnTick` 里调用的 `DrainPending` 解析成全局 nil，
> `pcall(nil, now)` 静默失败 → **一次跑出 27 个测试失败**，
> 而且实机上表现是"什么都不发生"。
>
> **同一个语言、同一个陷阱、两个不相干的项目都中招。**
> 这说明它不是巧合，是 **Lua 的固有坑**——而战锤3这个项目的对策是
> **把它变成第 3 道构建门禁（函数定义顺序 lint）**，从工程上根治。

### 4.2 `require` 返回 `true`

```lua
local ac_tactics = require("ac_tactics");
-- 如果模块文件没有 return 一个表，require 返回的是布尔 true！
```

**后果**：主脚本拿到 `true` 而不是模块表 → **所有规则静默失效**。

**防线**（代码里真的这么写了）：

```lua
local ok_require, ac_tactics = pcall(require, "ac_tactics");
if not ok_require then
    ...报错
elseif type(ac_tactics) ~= "table" then           -- ← 类型检查
    ac_tactics = _G.ac_tactics;                    -- ← 回退到全局
    if type(ac_tactics) ~= "table" then ac_tactics = nil; end;
end;
```

**"永远不信任返回值"**——这个习惯和黑猴那边"永远不信任引擎返回值"是同一套防御性编程。

### 4.3 `load_script_libraries()` 的双重构造陷阱

**症状**：每个单位都刷一条 CA 警告。

**原因**：

```
mod 脚本调用 load_script_libraries()
    → force_require lib_header → 重新执行一次
    → 创建【第二个】battle_manager 单例
    → 但单例守卫查的是【新 core 的静态表】，所以放行了
    → 新 bm 的 all_scriptunits 永久为空
    → get_scriptunit_for_unit 每次落空，刷一条警告
```

**修复**：**绝对不要调用它**——游戏在加载 mod 之前已经用默认战斗脚本完成库加载和 bm 构造了。

> **这是个"重复初始化破坏单例"的经典案例。** 而且守卫本身有缺陷
> （查错了表），所以没拦住。

### 4.4 攻城战：官方明确警告不要用 ai planner

设计文档里记着：

> **官方文档明确警告攻城战中不要用 ai planner**（攻城 AI 会覆盖单位行为）

**实测教训**（v2.4，20v20 攻城）：

- 强行下野战军级目标（`attack_force`）→ **与原生攻城 AI 冲突 → 动停震荡、零击杀**
- 纯移交（`SIEGE_SAFE`）→ 12 分钟消耗战，20→13 逐个战损后战败

**最终方案**：换思路——**"攻城挂机轻推"**：闲置超过 30 秒的单位就近攻击。

**这是"打不过就换策略"的实例，也是实测数据的价值。**

### 4.5 证伪：拉宽阵型无效

```lua
-- v3.7 实测证伪——increment_formation_width 在 planner 托管下无效
-- （原生 AI 用自己的阵型宽度覆盖，实测 17->17、22->22 无变化）。
-- 要真正控制宽度需线兵全手动控制，暂搁置。保留配置位以备将来。
line_widen = false,
```

**注意这段话的写法**：不是删掉了事，而是**把否定结论写进注释留在原地**。

> **记录"什么不行"，和记录"什么行"一样重要。**
> 否则下一个人（或三个月后的你）会再试一遍。

## 五、工程方法（这部分比技术更值得学）

### 5.1 五道构建门禁

```
① 语法检查（luaparse）
② 释放盾作用域 lint      ← 专治 4.1 那个 upvalue 坑
③ 函数定义顺序 lint      ← 同上，AST 级检查
④ 战术单元测试（51 断言）
⑤ 主脚本集成测试（7 断言）
        ↓
      打包安装
```

**这个流水线的精髓在于：②和③不是通用检查，而是"把自己踩过的坑变成自动检查"。**

> **每修一个 bug，就加一道能抓住它的门禁。**
> 这样同一个 bug 不可能犯第二次——**这是把调试成本转化为工程资产。**

### 5.2 离线测试框架

**用 `fengari`（纯 JS 实现的 Lua VM）+ 手写的游戏 API 桩**，在**不启动游戏**的情况下跑真实 mod 脚本。

```
test/test_tactics.lua   规则层测试（51 断言）
test/test_main.lua      主脚本集成测试（7 断言）
```

**为什么这很重要**：游戏内测试一轮要几分钟，还不可复现；离线测试一秒跑完，还能精确构造边界局面。

> **黑猴那个项目我也做了同样的事**（用 Python 的 `lupa` 起真实 Lua 5.4，
> 配一套 mock 的 UE4SS API + 虚拟时钟），最后是 **33 个场景 / 203 条断言**。
> **两个不相干的项目，都走到了同一个工程解法上**——
> 因为"没法快速验证"是所有 mod 开发的共同瓶颈。

### 5.3 数据驱动调参

**战损对照表**（README 里）：

| 版本 | 阵容 | 战损率 | 击杀比 | 时长 |
|---|---|---|---|---|
| v2.4 盾失效对照 | 20v20 | 81.7% | 0.54 | 325s |
| v3.7 | 14混+1骑+**5大型** vs 20 | **18.8%** | **4.86** | 306s |
| v3.7 | 14混+5骑+1炮 vs 20 | 92.4% | 0.85 | 494s |
| v3.12 | 14混+3骑 vs 18 | 39.2% | **3.99** | 244s |

**结论写得非常克制：**

> 规则层机制有效（第3场证明）；**战损上限由阵容克制决定**（第2场）。

**这就是科学态度**：不因为一次好成绩就宣称成功，而是指出"这个变量的影响比我的规则更大"。

**而且注意 v2.4 那一行标着"盾失效对照"**——**他们保留了失败版本的数据作为基线。** 没有对照组，81.7% 和 18.8% 都无法解释。

## 六、和黑猴项目的完整对照

| 维度 | 黑猴 auto-dodge | 战锤3 自动指挥 |
|---|---|---|
| **官方 mod 支持** | ❌ 无创意工坊、无接口 | ✅ **官方 Lua 沙箱** |
| **接入方式** | DLL 劫持（`version.dll`） | **丢个 .pack 进 data 目录** |
| **改行为的方式** | Harmony 改机器码入口 | **Lua 里替换函数引用** |
| **可靠性** | **随机**（实测 1/6） | **确定性** |
| **崩溃风险** | 有（虽非 mod 引起） | **几乎为零** |
| **能否查官方文档** | ❌ 只能反编译 | ✅ **有 API 文档** |
| **有没有参考实现** | ❌ 几乎没有 | ✅ **有（AI General III 等）** |
| **离线测试** | 自己搭（lupa + mock） | 自己搭（fengari + 桩） |
| **构建流水线** | 无 | **五道门禁** |
| **版本稳定性** | 游戏还在更新 | **已锁定版本** |
| **开发周期** | 折腾一整晚，最终不稳定 | 迭代到 v3.12，可复现有效 |

**两边的工程量其实差不多**——都做了离线测试框架、都踩了 Lua 的坑、都要处理"两个大脑抢控制权"。

**差别全在"游戏给不给你接口"：**

```
有官方接口 →  把力气花在"战术规则"上       →  能迭代到 v3.12
没有接口   →  把力气花在"怎么把代码塞进去"  →  塞进去了还不一定跑
```

## 七、回到你的问题：这印证了什么

你在上一轮问"换游戏第一反应该查什么"，我给的答案是"**先看生态，再看引擎**"。

**这个项目就是那句话的正面例证：**

**① 生态的第一要素是"有没有官方脚本接口"。**
有它，你的代码就是游戏的一部分（沙箱内、确定性地执行）；
没有它，你的代码就是个入侵者（要注入、要改机器码、可能被优化绕过）。

**② 同样的技术，在不同层上可靠性差一个数量级。**

| 手法 | 在哪一层 | 可靠性 |
|---|---|---|
| 猴子补丁 | **Lua 表查找** | **确定性** |
| 猴子补丁 | **机器码入口** | **随机** |

概念完全一样（"把那个函数换掉"），但一个查表必然命中，一个会被 JIT 内联绕过。

**③ "选层"比"写代码"重要得多。**
黑猴那个 mod 的作者代码写得没问题（6 个补丁的分工很清晰、还知道"调游戏现成的闪避函数而不是自己控制移动"），**但他的方案建立在一个不可靠的层上，所以再怎么写都只能靠运气。**

**④ 而战锤3这边，最难的从来不是"怎么把代码塞进去"（丢个文件就行），而是"战术规则怎么设计"。**
——**这才是 mod 开发本该有的样子：把精力花在你想实现的玩法上，而不是花在和游戏对抗上。**
